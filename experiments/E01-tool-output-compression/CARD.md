## 연구 질문과 가설
- 질문: 로컬 소형 코딩 모델(Qwen3.5-9B, thinking 끔)이 bash 하나만 가진 에이전트로 버그 수정 과제를 풀 때, 하네스가 모델에게 보내는 대화 기록에서 **가장 최근 5개 도구 출력만 전문으로 두고 그보다 오래된 도구 출력을 한 줄로 압축**하면, 모든 출력을 그대로 보내는 기준선 대비 해결률(숨겨진 테스트 통과율)이 바뀌는가. 토큰, 턴 수, 종료 사유는 어떻게 달라지는가.
- 가설과 근거: 해결률이 오르거나 같고, 입력 토큰은 줄 것으로 본다. 근거는 SWE-agent(arXiv 2405.15793)가 같은 조작으로 GPT-4 Turbo 의 SWE-bench Lite 해결률을 15.0% → 18.0% 로 올린 보고다. 소형 로컬 모델은 긴 문맥에서 수정 전·후 파일 내용을 혼동하거나 같은 명령을 반복하는 증상(AgentBench, arXiv 2308.03688)이 더 심하므로 효과가 더 클 수도 있고, 반대로 압축된 정보를 다시 조회하느라 턴을 낭비해 효과가 상쇄될 수도 있다. 어느 방향이든 그대로 보고한다.
- 용어: 이 실험에서 "도구 출력 압축"은 위 처리를 가리킨다. 모델이 아니라 하네스가 하는 일이다.

- 파일럿에서 튜닝에 사용한 태스크와 최종 평가 표본의 관계: 파일럿 10과제는 본 실험 표본에서 제외한다(`prepare_tasks.py --exclude`). 압축 기준 개수 5 는 SWE-agent 논문 값이며 파일럿 결과로 조정하지 않는다. 다른 값은 E02 로 분리한다.

## 보조 질문 (사전 등록, 2026-10-26): 쉬운 과제에서 압축은 비용을 바꾸는가

1차 통과에서 해결률이 두 조건 모두 100% 라 주요 지표로는 차이를 볼 수 없었다. 대신 과제별 토큰·턴 수가 양방향으로 흩어졌다(턴 수가 같은 5개 과제에서는 b 가 6% 적고, 1개 과제에서 b 가 두 배). 이것이 잡음인지 경향인지 보기 위해 다음을 **결과를 보기 전에** 정한다.

- 질문: 기준선이 거의 다 푸는 쉬운 과제(HumanEvalFix 원형)에서, 도구 출력 압축은 시도당 입력 토큰·턴 수·벽시계 시간을 바꾸는가. 해결률 차이는 이 묶음에서 기대하지 않는다.
- 가설: 방향을 정하지 않는다. 줄어들 수도(턴당 입력 감소), 늘어날 수도(압축된 정보를 다시 읽느라 턴 증가) 있다.
- 자료: (a) 사전 등록된 파일럿 `pilot-001` (10과제 × 2조건 × 5회). (b) 추가 묶음 `data/tasks_cost_study.json` (파일럿 10개를 제외하고 seed 20261027 로 뽑은 30과제) × 2조건 × 5회 = 300시도는 **보류**(2026-10-26, 담당자 결정: 기계 시간 3~4시간을 쓰기 전에 (a) 결과를 먼저 본다). 돌릴 경우 설정은 파일럿과 완전히 같게 하고 run id 는 `cost-001`.
- 지표: 과제별로 (b − a) 의 입력 토큰, 턴 수, 시간을 5회 평균으로 구해 짝지은 차이의 분포를 본다. 검정은 과제 단위 Wilcoxon 부호순위(양측). 반복 5회의 과제 내 분산도 보고해 비결정성 크기를 함께 보인다.
- 해석 기준: 짝지은 입력 토큰 차이의 95% 부트스트랩 구간이 0 을 포함하면 "차이 없음". 구간이 한쪽에 있어도 중앙값 차이가 5% 미만이면 "실질적 차이 없음".
- 이 분석은 보조다. E01 의 주요 질문(해결률)은 20~50% 구간의 묶음에서 따로 답한다. 이 묶음의 과제는 본 실험 표본으로 쓰지 않는다.

## 로그 공개 범위

`ls -l` 출력의 소유자 칸, 작업 디렉터리, 궤적 저장 경로에 로컬 사용자명과 홈·임시 경로가 들어간다. 공개 전에 `src/sanitize_logs.py` 로 레포 경로를 `<repo>`, 임시 경로를 `<tmp>`, 홈을 `~`, 사용자명을 `user` 로 바꿨다(세 실행 122개 궤적 파일). 바꾼 것은 문자열뿐이며 정리 전후 `harness/summarize.py` 결과가 같음을 확인했다. 토큰 수는 모델이 실제로 본 원문 기준이다. 이후 실행은 `run.py` 가 저장 시점에 같은 정리를 한다. 그 밖에 시크릿·API 키는 없다(로컬 추론).

## 해석과 한계
- 현재 근거로 말할 수 있는 것: mini-swe-agent 위의 실행 경로·채점기·토큰 기록·thinking 끄기가 실제 모델에서 동작하고, 압축이 설계대로 작동한다. HumanEvalFix 원형은 이 모델에게 너무 쉬워(100%) 해결률 차이를 측정할 수 없다. 개입 효과에 대해서는 아직 아무것도 말할 수 없다.
- 실패·부정적 결과 / 한계:
  - HumanEvalPack 은 공개 데이터라 모델이 학습 때 봤을 수 있다. 두 조건이 같은 과제를 쓰므로 비교는 공정하지만 절대 해결률은 과장될 수 있다.
  - 파일럿 샌드박스는 네트워크를 차단하지 않는다. 모델이 외부에서 정답을 가져올 가능성은 낮지만 0 이 아니다. 본 실험은 Docker `--network none`.
  - 문맥 초과 판정: Ollama 는 num_ctx 를 넘는 입력을 조용히 잘라낸다(그 자체가 숨은 문맥 관리). 하네스는 (1) 전송 전 문자 수 기반 추정이 32K 를 넘으면, (2) 응답의 prompt_eval_count 가 32K−64 이상이면 "문맥 초과" 로 종료한다. 추정은 보수적이어서 실제보다 일찍 끊을 수 있다.
  - Ollama 는 앞부분이 같은 입력의 KV 캐시를 재사용한다. baseline 은 기록이 뒤에만 붙어 캐시 혜택을 크게 받고 intervention 은 압축 때문에 앞부분이 바뀌어 혜택이 줄 수 있다. 벽시계 시간은 이 비대칭을 고려해 해석하고, 비용 1차 지표는 토큰 수로 한다.
  - 파일 하나짜리 과제라 궤적이 짧으면 압축이 작동하지 않을 수 있다. 선정 기준 (2) 로 걸러낸다.
- 아직 확인하지 못한 것: 20~50% 구간에 들어오는 과제 묶음. 100시도 모두 성공이라 종료 사유 분포·반복 궤적·거짓 성공 지표는 아직 의미 있는 값이 없다. 쉬운 과제의 비용 효과는 10과제로는 구간이 0 을 걸쳐 확정 못 함(30과제 추가 묶음은 보류).
