# 스킬 적용 전 확인은 언제 에이전트의 실패를 줄이는가?

> 이 문서는 v5 이전 결과의 비판적 검토와 이전 재실행 기록입니다. 보강 실험 180회의 최신 결과와 기술보고서 파트는 [E02 기술보고서](../../../../report/e02-skill-precheck.md)에 정리했습니다.

장현서 · AgentProof W6 연구 결과 검토 · 2026-11-09

## 초록

본 연구는 현재 환경과 맞지 않는 절차적 스킬을 받은 에이전트에게 적용 전 확인 메시지를 제공하면 최종 산출물 성공률이 회복되는지를 살핀다. 완료된 두 파일럿 확장 실행을 재분석했다. 통제 과제 실험은 3개 과제에 스킬 적합성, 근거 위치, 확인 메시지를 교차한 240회 실행이다. 공개 벤치마크 실험은 SkillsBench 6개 과제에 스킬 적합성과 확인 방식을 교차한 216회 실행이다. 두 실험의 과제·문구·실행 환경이 달라 결과를 합산하지 않았다.

통제 과제에서 스킬이 어긋나고 근거 파일이 지시되지 않았을 때, 기준선과 일반 확인은 각각 0/15, 위치 유형을 안내한 확인은 9/15에 성공했다. 회복은 graph와 csv에서 관찰됐고 events에서는 관찰되지 않았다. 과제를 추론 단위로 둔 차이의 부트스트랩 구간은 0~100%p로, 평균 +60%p만으로 과제 일반화를 주장할 수 없다. SkillsBench에서는 변경 스킬이 기준선 성능을 낮추는 조작 확인이 성립하지 않았다. 사후 검증의 이득은 일부 과제에 집중되고 오류 처리 방식에 민감했다.

따라서 현재 결과는 **일부 통제 과제에서 근거 탐색을 유도하는 확인 메시지가 도움이 될 수 있다는 제한적 증거**를 제공한다. 일반적인 확인 메시지의 효과, 잘못된 스킬로부터의 일반적 회복, 사후 검증의 고유 효과는 아직 확립하지 못했다.

이 문서는 완료된 원자료를 근거로 썼다. 진행 중인 2026-11-09 추가 실행은 완료 전까지 아래 결론의 근거로 사용하지 않는다. 장표 제작에 앞서 결과의 해석 범위를 고정하기 위한 검토다.

## 1. 연구 질문과 식별하려는 효과

출발 질문은 “스킬을 읽은 뒤 확인하라고 지시하면 성공률이 오르는가?”다. 그러나 다음 세 효과를 구분해야 한다.

1. **스킬 불일치의 피해:** 같은 과제에서 정상 스킬 또는 환경에 비해 불일치 조건이 성공률을 낮추는가?
2. **불일치 회복:** 확인 개입의 이득이 정상 조건보다 불일치 조건에서 더 큰가?
3. **일반적인 추가 검증의 이득:** 불일치 여부와 관계없이 더 확인하거나 더 오래 실행해서 좋아지는가?

검증 메시지가 있는 조건의 성공률이 높다는 사실만으로 2번을 입증할 수 없다. 불일치로 인한 피해를 먼저 확인하고, 개입 효과가 정상 조건에서도 비슷한지 비교해야 한다.

주 결과는 산출물이 결정적 채점 기준을 모두 통과하고 에이전트가 정상 종료한 비율이다. 에이전트가 “확인했다” 또는 “완료했다”고 말했는지는 성공 판정이 아니다. 비용과 근거 열람 행동은 별도로 분석한다.

| 과제 | graph, csv, events | threejs, econ, crystallographic, dapt, r2r, llm-prefix |

| 조건 | A 스킬 없음 / B 스킬만 / C 일반 확인 / C2 위치 유형 안내 | A / B / C / C2 전제 대상 확인 / P 사전+사후 / S 스킬 경계 정보 |

| 사용 비용 | $2.191515 | $10.742001 |

공통 모델은 `gpt-5.4-mini-2026-03-17`, reasoning effort low다. 도구와 실행 한도는 실험 묶음 안에서 조건 간 같게 두었다. v3와 v4의 C2는 동일 문구가 아니다. v3는 파일 종류를 알려주고 v4는 절차의 구체 전제 값을 대조하라고 한다. 따라서 두 C2를 하나의 동일 처리로 합치거나 두 묶음의 절대 성공률을 직접 비교하지 않는다.

통제 과제에서 L2/L3는 동일 과제 내 비교가 가능하다. SkillsBench의 “지시문에 근거가 있음/다른 파일에 있음”은 과제와 함께 달라지는 특성으로, 가시성만의 인과 효과를 식별하지 못한다.

분석에 무효 실행 `main-001`은 사용하지 않았다. `results/main`과 `results/sb/main`의 이름과 달리 두 실행 모두 최종 설계 이전의 파일럿이다.

## 3. 결과 1: 통제 과제에서는 근거 위치가 기준선 실패를 갈랐다

### 3.1 조작 확인

불일치 E1의 B는 근거 파일이 계약에 지시된 L2에서 15/15, 지시되지 않은 L3에서 0/15였다. 과제별로도 세 과제 모두 5/5 대 0/5다. 정상 E0의 B는 L2와 L3 모두 합쳐 30/30이었다.

즉 이 통제 환경에서는 스킬의 불일치 자체보다 **현재 요구사항의 근거에 접근하는 경로**가 실패를 크게 좌우했다. “틀린 스킬을 주면 항상 실패한다”는 해석은 맞지 않는다. 근거 파일이 지시되면 같은 스킬 불일치에서도 B가 성공했다.

### 3.2 불일치·근거 미지시(E1/L3)의 개입 효과

| 과제 | A 스킬 없음 | B 스킬만 | C 일반 확인 | C2 위치 유형 안내 | C2−B |
|---|---:|---:|---:|---:|---:|
| graph | 5/5 | 0/5 | 0/5 | 5/5 | +100%p |
| csv | 1/5 | 0/5 | 0/5 | 4/5 | +80%p |
| events | 0/5 | 0/5 | 0/5 | 0/5 | 0%p |
| 합계 | 6/15 | 0/15 | 0/15 | 9/15 | +60%p |

B와 C가 모두 0/15라는 관찰은 “이 설정에서 일반 확인의 회복을 관찰하지 못했다”는 뜻이다. 바닥 성능과 작은 표본 때문에 일반 확인의 효과가 정확히 0이라는 뜻은 아니다. 기존 trial 단위 Newcombe 구간도 C−B에 대해 약 −20.4~+20.4%p였다.

C2−B의 기존 카드 구간은 trial을 독립으로 취급해 +28.3~+80.2%p다. 하지만 같은 과제의 반복 실행은 새로운 과제 표본 15개가 아니다. 과제별 차이(100, 80, 0%p)를 동등하게 가중하고 과제 3개를 재표집한 기술적 95% 구간은 **0~100%p**다. 넓은 구간과 events의 0/5를 함께 보고해야 한다. 이 결과를 “일반적인 스킬 오적용을 방지했다”로 확대할 수 없다.

### 3.3 정상·근거 지시 조건의 부작용

| 비교 칸 | B | C | C2 | 해석 |
|---|---:|---:|---:|---|
| E0, L2+L3 | 30/30 | 27/30 | 30/30 | C2 손해는 관찰되지 않았지만 무해성을 입증한 것은 아님 |
| E1, L2 | 15/15 | 15/15 | 13/15 | C2가 근거 지시 상황에서도 항상 도움이 되지는 않음 |
| E1, L2, events만 | 5/5 | 5/5 | 3/5 | 확인 개입 뒤 실패하는 사례가 존재 |

따라서 “C2가 정상 상황에서는 손해 없이 회복한다”는 문장은 E0의 제한된 표본에 한정해야 한다. 같은 실험의 다른 칸에서는 C2가 더 낮았다. 이 차이가 우연인지 개입 때문인지는 추가 표본과 실패 분석이 필요하다.

## 4. 결과 2: 근거 탐색과 근거 적용은 분리된다

E1/L3에서 근거 파일 경로가 도구 인자에 나타난 실행은 B 0/15, C 0/15, C2 11/15였다. C2의 해당 11회 중 9회가 성공했고, 나머지 4회는 모두 실패했다.

이는 “위치 유형 안내가 근거 탐색을 유도했을 가능성”과 양립한다. 다만 파일을 여는 행동은 무작위 배정한 별도 요인이 아니다. 열람 여부는 모델의 다른 판단과 함께 달라지므로 9/11 대 0/4를 열람의 인과 효과나 정식 매개 효과로 해석하지 않는다. 또한 기존 `evidence_opened`는 도구 인자에 파일명·경로가 등장했는지로 판정하는 대리 지표다.

### 실제 실패 궤적

`main-002 / events-E1-L3-C2-r1`에서 다음을 직접 확인했다.

1. trace items[10–11]: `config/report.json`을 읽고 `report_timezone: Asia/Seoul`을 반환받았다.
2. items[19]: 집계 코드에서 `day=row['ts_utc'][:10]`으로 UTC 문자열의 날짜를 사용했다.
3. items[25]: 그 UTC 집계 결과를 산출물로 저장했다.
4. 외부 채점: `failure`, 이유 `premise_from_other_env`.

E1 전체에서 events C2가 근거 파일을 연 7회 중 4회는 실패했다. 이 사례는 **근거를 찾게 하는 개입과, 찾은 근거를 우선하여 절차를 수정하게 하는 개입이 서로 다를 수 있음**을 보여준다. 단일 궤적만으로 앵커링이 유일한 원인이라고 단정하지 않는다. 지시 우선순위 해석, 시간대 변환 능력, 검증 누락도 대안 설명이다.

## 5. 결과 3: SkillsBench에서는 불일치 피해가 확인되지 않았다

### 5.1 기준선의 조작 확인

| 환경 | B 성공 |
|---|---:|
| E0 원본 스킬 | 11/18 |
| E1 변경 스킬 | 13/18 |
| E0−E1 | −11.1%p |

이 실험에서는 스킬 전제 값을 바꿨을 때 기준선 성공률이 낮아진다는 증거를 확보하지 못했다. “피해가 없다”를 입증한 것도 아니다. 과제 6개 × 3회로 작고, 과제마다 변경의 영향이 다르다.

사전 oracle 점검에서 변경 값을 그대로 쓰면 verifier가 실패했다는 사실과, 실제 에이전트가 그 값을 따라 성능이 떨어진다는 사실은 다르다. 전자는 채점·조작의 기술적 유효성이고, 후자는 모델 행동 수준의 조작 확인이다. 후자가 성립하지 않으면 확인 개입의 효과를 “불일치 피해의 회복”으로 식별하기 어렵다.

4개 과제는 정답 값이 지시문에 있어 스킬과 충돌할 때 모델이 지시문을 따를 수 있었다. 이는 설명 후보이며, 가시성을 무작위 조작하지 않은 이 결과만으로 원인을 확정하지 않는다.

### 5.2 E1의 조건별 결과

아래는 API 오류도 비성공으로 포함한 실행 기준 분모다.

| 과제 | B | C2 | P | P−C2 |
|---|---:|---:|---:|---:|
| threejs | 2/3 | 3/3 | 3/3 | 0%p |
| econ | 2/3 | 3/3 | 3/3 | 0%p |
| crystallographic | 3/3 | 3/3 | 2/3* | −33.3%p |
| dapt | 2/3 | 1/3 | 2/3 | +33.3%p |
| r2r | 2/3 | 1/3 | 3/3 | +66.7%p |
| llm-prefix | 2/3 | 1/3 | 3/3 | +66.7%p |
| 합계 | 13/18 | 12/18 | 16/18 | +22.2%p |

*crystallographic P에 API 오류 1회 포함. 그 오류를 산출물의 기능 실패로 분류하지는 않으며, 실행 정책의 성공률 분모에 남겼다.*

- C2−B: −5.6%p, 과제 부트스트랩 구간 −27.8~+16.7%p.
- P−C2: +22.2%p, 과제 부트스트랩 구간 −5.6~+50.0%p.
- P−B: +16.7%p, 과제 부트스트랩 구간 −5.6~+33.3%p.

P의 이득은 주로 r2r·llm-prefix, 일부 dapt에서 발생했다. 올바른 값이 지시문에 있는 4개 과제만 보면 P와 C2는 모두 10/12다. 따라서 평균의 증가가 넓은 범위의 과제에서 반복된다고 볼 수 없다.

### 5.3 오류 제외 분석과 민감도

v4의 P−C2는 사전 등록된 부차 비교(H2)다. 사후에 만들어 낸 비교라고 부르지는 않는다. 다만 등록된 9개 비교 중 하나이며, 이를 본 뒤 P를 후속 연구의 중심으로 고르는 데는 선택의 문제가 남는다.

기존 카드는 API 오류를 제외하여 P 16/17 대 C2 12/18, 차이 +27.5%p, 구간 +4.9~+50.0%p를 보고했다. 이 처리는 기존 분석 방침이며 지우지 않는다. 다만 오류를 포함하면 구간이 0을 포함하므로 **긍정적 불확실성 판단이 오류 처리에 민감함**을 함께 보고한다. 두 분석 중 더 좋아 보이는 것만 고르면 안 된다.

### 5.4 일반 검증 효과와 불일치 회복의 구분

P−B는 E1에서 +16.7%p지만 E0에서도 +11.1%p다. 차이의 차이 `[P−B]E1 − [P−B]E0`는 +5.6%p이며, 과제 재표집 구간은 약 −22.2~+33.3%p다. 이는 추가 검증의 이득이 불일치 조건에 특별히 집중된다는 증거가 부족함을 뜻한다.

P는 완료를 한 번 보류하고 검증 메시지를 추가한다. 현재 비교에는 같은 추가 턴을 주는 위약 N과 사후 검증만 하는 V가 없다. 추가 실행 기회, 일반적인 재검토, 확인 문구 자체의 효과가 분리되지 않았다.

### 5.5 실패 테스트를 보면 성공률 차이의 의미가 달라진다

E1의 B·C2·P 비성공 trial 13개에 대해 공식 verifier의 로그를 확인했다. 다음은 그중 중요한 구분이다.

| 실행 | 실패한 항목 또는 중단 이유 | 해석 가능한 범위 |
|---|---|---|

이 항목들은 결과를 본 뒤 수행한 **탐색적 실패 분해**다. 사전에 정한 주 지표를 바꾸거나 과제를 제외하는 근거로 쓰지 않는다. 특히 dapt C2의 실패가 밀도 검증이 아니라 분류·집계 검증에서 발생했다는 점, r2r의 실패가 서로 다른 항목이라는 점은 P의 평균 우위를 “잘못된 스킬의 전제를 고친 효과”로 단순 해석할 수 없게 한다.

원 로그에서 추출한 행과 trial 좌표는 `pilot_failure_audit.json`에 보존했다. 로그는 tail만 남아 있는 경우가 있어, 빈 추출 결과를 실패 항목이 없다는 뜻으로 해석하지 않는다.

### 5.6 실패했어도 변경된 스킬의 전제를 따른 것은 아니었다

세 궤적에서 에이전트가 실제 작성한 코드를 추가로 대조했다.

| 실패 trial | E1 스킬에 넣은 값 | 에이전트가 실제 쓴 값 | 관찰 |
|---|---|---|---|
| threejs E1 B r1 | `makeRotationX(+π/2)` | `makeRotationX(-Math.PI / 2)` | 원본 방향을 썼지만 geometry verifier 실패 |
| econ E1 B r2 | HP `λ=6.25` | 두 계열 모두 `hpfilter(..., lamb=100)` | 원본 λ를 썼지만 상관계수 오차로 실패 |
| r2r E1 C2 r1 | `−R/J`, `1/J` | 행렬에 `−R**2/J`, `R/J` | 원본 계수를 썼지만 전체 선형화 행렬 검증 실패 |

이 세 사례에서 **전체 과제 실패를 곧바로 스킬 오적용으로 분류하면 오분류**가 된다. 현재 지표는 최종 과제 성공을 정확히 측정하지만, 그 실패가 조작한 전제 때문인지는 별도 확인해야 한다. 실패율만으로 “앵커링이 줄었다”거나 “잘못된 전제를 교정했다”고 주장하지 않는다.

이 점은 본실험에서 주 성공 지표를 유지하면서도, **변경 전제 사용 여부와 그 전제에 직접 연결된 verifier 항목**을 보조 지표로 기록해야 할 이유다. 위 세 사례는 수작업으로 확인한 예시이며 전체 실패의 발생률 추정은 아니다.

## 7. 타당성 위협

- **과제 표본:** 반복 실행 수와 독립 과제 수는 다르다. 통제 과제 3개, 공개 과제 6개로 추론 범위가 작다. 작은 클러스터 수의 부트스트랩도 정밀한 일반화를 보장하지 않는다.
- **선택과 적응:** v3와 최종 설계는 앞선 파일럿을 보고 정했다. v4의 P−C2는 실행 전 등록된 부차 비교(H2)이지만 주 비교는 C2−B이며, 등록 비교 9개 중 하나다. 이번 추가 실행에서 P를 선택한 것은 기존 P 신호를 본 뒤의 선택이다. 실행 전 등록한 부차 비교와 결과를 본 뒤의 후속 선택을 구분한다.
- **개입의 내용:** v3 C2는 실제 근거와 맞는 파일 종류를 알려준다. “확인”의 효과와 유용한 탐색 힌트의 효과가 분리되지 않았다.
- **불일치의 대표성:** 연구자가 만든 전제 불일치다. 자연 발생 스킬 오류를 대표한다고 보장하지 않는다.
- **공개 벤치마크의 가시성:** 값이 지시문에 있는지 여부가 과제 정체성·난도와 얽혀 있다. 직접 조작 없이 근거 가시성의 인과 효과로 해석하지 않는다.
- **비교 조건:** P의 추가 턴 효과와 사후 검증 효과를 분리할 위약·단독 조건이 없다.
- **행동 측정:** 파일 경로 등장만으로 실제 열람·이해·반영을 단정하지 않는다.
- **실행 환경:** v3는 완전 격리 컨테이너가 아니다. v4 verifier는 네트워크에 연결된다. 최종 설계의 완전 오프라인 실행 요건과 다르다.
- **단일 모델:** 다른 모델·reasoning effort·하네스로 일반화할 수 없다.
- **오류 처리:** SkillsBench API 오류 제외 여부가 구간 해석에 영향을 준다. 두 분모를 공개한다.

## 8. 현재 허용되는 결론

**쓸 수 있는 주장:** 이 통제 과제군에서는 근거 파일이 지시되지 않은 불일치 조건에서 기준선이 실패했고, 근거 위치 유형을 안내한 확인 메시지가 graph와 csv의 일부 실패를 회복했다. events에서는 근거를 읽은 뒤에도 잘못된 절차를 적용하는 실패가 남았다. 공개 과제의 사후 검증은 후속 검증이 필요한 탐색적 신호다.

**아직 입증하지 못한 주장:** 일반 확인 메시지의 보편적 효과, 스킬 불일치에서의 일반적인 회복, 사후 검증의 고유 효과, 과제 전반의 무해성, 실제 서비스의 비용 효율.

발표의 중심은 “확인 지침을 붙이면 좋아진다”라는 평균 비교보다, **어떤 단계에서 실패했으며 현재 실험이 어떤 효과를 식별할 수 있는가**에 두는 것이 맞다.

## 9. 다음 실험의 우선순위

1. **가시성 조작의 행동상 유효성 확인:** 공개 과제에서 근거를 숨긴 뒤 B의 불일치 피해가 실제로 생기는지, 정상 E0의 과제 수행 자체를 파괴하지는 않는지 점검한다.
2. **사전 확인의 탐색 힌트 분리:** 파일 종류를 직접 말하지 않는 문구, 단순 파일 목록 확인, 전제 대조를 구분한다. 현 최종 설계의 C2는 기존 v3 C2와 다르므로 새 처리로 다룬다.
3. **추가 턴과 검증의 분리:** N, C2, V, P를 비교하고 E0/E1의 상호작용을 본다. P의 단순 평균 우위를 불일치 회복으로 간주하지 않는다.
4. **실패 테스트와 실제 행동 연결:** 근거를 못 찾음 / 찾고도 무시 / 적용했지만 계산·구현 실패를 구분한다. 일부 궤적을 수작업 검토해 자동 지표의 정확도도 확인한다.

진행 중인 추가 실행은 기존 v3/v4의 재현이다. 새 입력과 확률적 반복에 대한 안정성 점검에는 도움이 되지만, 위 식별 문제를 해결하는 최종 설계 본실험을 대신하지 못한다. 완료되면 이 문서의 별도 절에 기존 결과와 나란히 추가한다.
