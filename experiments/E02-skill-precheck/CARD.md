## 연구 질문과 가설
- 질문: 스킬이 현재 과제와 안 맞을 수도 있을 때, 하네스가 스킬을 읽은 직후 적용 전 확인 메시지를 한 번 넣으면 최종 산출물 성공률이 오르는가? 스킬이 맞을 때는 손해가 없는가? 효과가 있다면 **확인 메시지가 무엇을 담아야** 하는가?
- 근거: SkillsBench(스킬 적용 실패 사례, 길이 맞춘 기준선 필요성), SWE-Skills-Bench(surface anchoring), Demystifying Agent Skills(지침 오적용 10.0%, 완화책 미검증), SLBench/SLGuard(확인 지침 아이디어 — 이 실험은 새 방법 주장이 아니라 통제 비교).
- v2 파일럿(아래)에서 일반 확인 메시지(C)는 효과가 없었고, 에이전트가 원래 읽지 않는 파일에 근거가 있으면 B·C 모두 실패했다. v3는 이 관찰을 **근거 위치**라는 요인과 **위치 유형을 알려주는 확인 메시지(C2)** 로 검증한다.

## 최종 설계 (2026-10-27 확정, 독립 검토 반영 — 본실험 전 사전 등록)

### 파일럿에서 얻은 근거 (수치는 원자료에서 다시 계산함)
1. **틀린 스킬의 피해는 근거가 숨어 있을 때 컸다.** 파일럿 2차 E1에서 B는 근거가 지시된 경우(L2) 15/15, 숨은 경우(L3) 0/15였다. 파일럿 3차(SkillsBench)에서는 틀린 스킬이 B를 낮추지 않았다(E0 11/18, E1 13/18). 그 6개 과제 중 4개는 올바른 값이 지시문에 있었다.
2. **일반 확인 메시지(C)는 근거가 숨은 상황에서 효과가 없었다**(1차 0%p, 2차 E1·L3 0/15 vs 0/15). 3차에서는 판단하기 어렵다(E1 +5.6%p 구간 [−27.8, +27.8]. 사전 등록하지 않은 E0 C − B는 +15.4%p [+4.0, +27.8]).
3. **확인할 곳을 구체적으로 알려준 사전 확인은 근거가 숨은 상황에서 효과가 컸다.** 2차 E1·L3에서 C2 − B는 +60%p [+28, +80]였다. 다만 효과는 graph·csv에서만 나왔고 events는 0/5였다. 그 C2 문구는 근거 파일 종류(소비자 코드·설정·출처 메타데이터)를 알려줬다는 한계가 있다.
4. **사후 검증은 탐색적 신호만 있다.** 3차 E1 P − C2 +27.5%p는 r2r·llm-prefix(각각 3/3 vs 1/3)와 dapt에서 나왔다. 근거가 지시문에 있는 4개 과제만 보면 10/11 vs 10/12(+7.6%p)다. P는 사후에 고른 조건이고, 비교 상대 C2(12/18)가 가장 낮은 축이었다.
5. **근거를 읽고도 스킬을 따르는 실패가 있다.** 2차 events에서 C2가 근거 파일을 연 7회 중 4회는 스킬대로 UTC로 묶어 실패했다.
6. 스킬 쪽 경계 정보(S)는 근거를 보여주지 못했다(3차 E1 −16.7%p, 구간이 0 포함). 스킬 자체의 이득은 컸다(A 6/34 vs B 24/36).

### 최종 연구 질문
> 스킬의 전제가 현재 환경과 어긋날 때, 그 피해는 **올바른 근거가 얼마나 드러나 있는지**에 따라 달라지는가? 근거가 숨어 있을 때 **적용 전 확인**(그리고 탐색적으로 **완료 전 검증**)은 성공률을 회복하는가?

주 질문은 처음 연구 질문인 "적용 전 확인"을 유지한다. 파일럿에서 가장 좋아 보인 조건(P)을 주 가설로 올리지 않는다.

### 요인
- **불일치 env**: E0 = 스킬 전제가 환경과 맞음, E1 = 어긋남. 만드는 방식은 두 가지이고, 묶음별로 따로 보고한다.
  - T1(SkillsBench): 스킬의 전제 값 하나를 다른 환경에서는 맞는 값으로 바꾼다. 과제·데이터·oracle·verifier는 그대로다.
  - T3(통제 과제): 스킬은 고정하고 환경(근거 파일과 정답)을 바꾼다. 파일럿 2차와 같은 방식이다.
- **근거 가시성 vis**:
  - T1: Visible(원본 task.md에 값이 있음) / Hidden(그 문장에서 값을 빼고, 언급되지 않는 사양 파일로 옮김)
  - T3: Pointed(계약이 근거 파일을 가리킴) / Hidden(언급 없음)
- **조건 cond (5개)**. 모든 메시지는 같은 자리에 1회만 넣고, 특정 파일·값·정답은 말하지 않는다.

| 조건 | 스킬 출력 직후 | 첫 완료 시도 때 (완료를 1회 보류) | 역할 |
| --- | --- | --- | --- |
| **B** | — | — | 기준선 |
| **N** | 중립 메시지("계속 진행하세요.") | 중립 메시지("작업을 마쳤다면 완료를 알리세요.") | 위약: 추가 턴·메시지 자체의 효과 통제 |
| **C2** | 사전 확인: 절차의 구체 값 1~2개를 골라, **작업 공간 파일 목록부터 확인**하고 지시문·데이터·문서·설정·코드의 근거와 대조 | 중립 | 주 개입 |
| **V** | 중립 | 사후 검증: 결과물의 핵심 값이 지시문·작업 공간 근거와 맞는지 확인하고 다르면 수정 | 사후 검증 단독 |
| **P** | 사전 확인 | 사후 검증 | 결합 |

- C2 문구는 파일럿 3차 문구에 "작업 공간 파일 목록부터 확인"을 더한 것이다. 파일 종류는 말하지 않는다(파일럿 2차 문구의 한계를 피함). 문구는 이 문서로 고정하고, 점검 실행 결과를 보고 바꾸지 않는다.
- 뺀 조건: C·S·A는 파일럿 기록으로만 남긴다.

### 과제 7개

| 묶음 | 과제 | 전제 (E0 / E1) | 가시성 |
| --- | --- | --- | --- |
| T1 SkillsBench | threejs-to-obj | X축 회전 −90° / +90° | Visible / Hidden |
| | econ-detrending-correlation | HP λ 100 / 6.25 | Visible / Hidden |
| | crystallographic-wyckoff | 분모 상한 12 / 8 | Visible / Hidden (예시 출력에 분모 9가 남는 누설 있음, 그대로 보고) |
| | dapt-intrusion-detection | 밀도 n(n−1) / n(n−1)/2 | Visible / Hidden |
| T3 통제 | graph / csv / events | 간선 키 / 쉼표 표기 / 날짜 기준 시간대 | Pointed / Hidden |

- 뺀 과제는 두 개다.
  - r2r: 파일럿 3차에서 E0 B가 0/3으로 바닥이었다. 원본이 이미 근거를 다른 파일에 두고 있어서 가시성을 조작할 수 없다.
  - llm-prefix: 원본이 근거 파일을 가리키는 형태라 숨길 수 없다.
  - 두 과제가 3차의 P 신호를 만든 과제라는 점을 기록해 둔다.
- 과제 고정 규칙: 본실험 전 점검을 통과한 과제만 쓴다. 기준은 oracle 1.0, E1 oracle < 1.0, Hidden 변형은 지시문에 값이 없고 사양 파일에만 있음, verifier 의존성은 이미지에 미리 설치. 결과를 보고 과제를 빼지 않는다.

### 환경
- 실행: 과제마다 Docker 이미지를 쓴다(T1은 SkillsBench `f860ecf`, T3는 같은 형식으로 포팅). trial마다 새 컨테이너를 띄우고, 에이전트 단계는 네트워크를 끊는다. verifier 단계도 의존성을 미리 넣어서 네트워크 없이 돌린다. 컨테이너당 CPU 2개·메모리 3GB, 동시 3개.
- 에이전트: 도구 4개, 첫 호출은 read_skill로 강제. trial당 요청 40·도구 40·900초, 자동 재시도 없음. 인프라 오류가 3회 연속 나면 멈추고, 같은 run-id로 **이어서 실행**할 수 있게 한다.
- 모델: gpt-5.4-mini-2026-03-17 (reasoning low). 재현은 gpt-5.4-2026-03-05로 Hidden 칸만 돌린다.
- 성공 = verifier reward 1.0 + 정상 종료. 실패한 테스트 이름을 기록해서, 실패가 불일치 탓인지 다른 오류 탓인지 가른다.

- **판정 규칙 (H1)**: 7개 과제를 합친 차이의 과제 단위 부트스트랩 95% 구간이 0을 넘고, **T1(SkillsBench) 4개 과제 중 3개 이상에서 방향이 같을 때만** "지지"로 쓴다. T3만으로 나온 효과는 "통제 과제에서만 관찰"로 쓴다.
- 보조 분석: 과제별 부호 검정과 순열 검정, 과제 무작위효과 로지스틱 회귀.
- 검정력 (H1 판정 규칙 기준, 과제 7개 × 칸당 5회, 시뮬레이션 400회, `sb/power_sim.py`): 모든 과제에 같은 효과일 때 +20%p → 0.36~0.44, +40%p → 0.88~0.90, +60%p → 0.99 이상. 효과가 과제 절반에만 있으면(파일럿 2차처럼) +40%p 평균 효과도 0.32~0.35, +60%p 평균 효과도 0.40~0.52다. 즉 이 설계는 **크고 고르게 나타나는 효과만 확증**할 수 있다. 일부 과제에만 나타나는 효과는 과제별 수치로 보고하고 확증하지 않는다. H2~H4는 탐색이다.

### 한계 (확정 시점 기록)
- 불일치는 실험자가 만든 것이다. E1 값은 실제로 다른 환경에서 쓰이는 값이지만 자연 발생 표본은 아니다.

## 파일럿 3차 설계 — SkillsBench 원본 과제 (사전 등록: 2026-10-27, 실행 전에 고정)

v3는 직접 만든 과제 3개라는 한계가 있었다(효과가 graph·csv에서만 나옴, events 0/5). 그래서 v4는 공개 벤치마크의 실제 과제·스킬·oracle·공식 verifier를 그대로 쓰고, **스킬의 전제 값 하나만** "다른 환경에서는 맞는 값"으로 바꿔 불일치를 만든다(10/13 초안의 방식).

## 파일럿 2차 설계 — 근거 위치 요인 (사전 등록: 2026-10-27, 실행 전에 고정)

### 요인
- **환경 env:** E0 = 스킬 전제가 맞음, E1 = 전제 하나가 다름. **입력 파일은 E0·E1에서 바이트 단위로 같고**, 근거 파일 하나만 다르다. 계약(`target_contract.json`)도 E0·E1이 같다.
- **근거 위치 loc:** L2 = 계약에 "입력 해석과 출력 형식의 세부 사항은 `<근거 파일>`에 정해진 대로 따를 것" 한 줄이 있음. L3 = 근거 파일은 작업 공간에 있지만 어디에도 언급되지 않음.
- **조건:** A 스킬 없음(참조) / **B 스킬만(기준선)** / **C 스킬 + 일반 확인 메시지** / **C2 스킬 + 위치 유형 확인 메시지**. C와 C2는 같은 자리(스킬 출력 직후 1회), 비슷한 길이다.

| 과제 | 스킬 전제 (E0) | E1 | 근거 파일 |
| --- | --- | --- | --- |
| graph | 간선 키 `from/to` (SkillsBench dialogue-graph `Edge.to_dict`) | 소비자가 `source/target` 요구 | `consumer/importer.py` |
| csv | 쉼표 = 소수점 (SkillsBench lab-unit-harmonization `parse_value`) | 쉼표 = 천 단위 | `meta/source.json` |
| events | UTC 날짜로 묶기 (자체 작성) | 서울 날짜 기준 | `config/report.json` |

- csv는 모든 값을 `12,345`처럼 쉼표 하나 + 세 자리로 만들어 **데이터만으로는 표기를 판별할 수 없게** 했다(E0 → 12.345, E1 → 12345.000). v2에서는 데이터 자체가 표기를 드러내 천장이었다.
- C 메시지: "방금 제공된 절차를 적용하기 전에, 결과에 영향을 주는 전제 1~2개를 현재 과제·입력 파일·환경의 근거와 대조하세요. …" (v2와 동일)

### 기제와 실패 양상
- **근거 파일 열람 (E1·L3):** B 0/15, C 0/15, C2 11/15. C2가 근거를 열었을 때 9/11 성공, 열지 않았을 때 0/4 성공. C2의 효과는 "근거 파일을 찾게 만든 것"으로 설명된다.
- **근거를 보고도 스킬을 따른 실패 (events):** E1·L3에서 C2는 2/5회 `config/report.json`(`Asia/Seoul`)을 열고도 UTC로 묶었고, 5회 모두 실패했다. 근거가 계약에 지시된 E1·L2에서도 C2는 2/5회 같은 방식으로 실패했다(B는 5/5 성공, 사전 등록 외 관찰). 확인은 했지만 적용 단계에서 스킬에 끌려간 사례다.

### 해석
- **주 가설(P1)은 지지된다.** 단, 효과는 과제 3개 중 2개에서만 나왔다(graph 5/5, csv 4/5, events 0/5). "위치 유형을 알려주는 확인은 원래 보지 않던 근거를 찾게 만들고, 찾으면 대부분 바로잡는다"까지는 말할 수 있다. "모든 불일치를 바로잡는다"는 말할 수 없다.
- **일반 확인 메시지(C)는 두 번의 독립 실행(v2 파일럿, v3 확장 실행)에서 모두 효과가 없었다.** E0에서는 −10%p 경향을 보였다(CI가 0을 포함).
- **C2의 대가:** 정상 상황(E0) 손해는 관찰되지 않았다(30/30). 비용은 trial당 +37%다.
- **남은 문제:** 근거를 찾은 뒤에도 스킬의 절차를 그대로 따르는 실패(events)가 남는다. 확인 단계가 아니라 적용 단계의 문제로, 후속 질문이다.
- **한계:** C2가 말하는 위치 유형이 이 실험의 근거 종류와 같다(사전 기록). 과제 3개 중 1개는 자체 작성이고, 모델은 1개다. CI는 trial을 독립으로 가정하므로 과제 군집을 반영하지 않는다(과제별 수치 참고). 파일럿을 보고 과제 템플릿(v2→v3)을 정했지만, 확장 실행 입력은 파일럿에 쓰지 않았다.
