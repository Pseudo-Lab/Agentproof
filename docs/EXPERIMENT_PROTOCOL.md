# 공통 실험·결과 규칙

## 비교 단위

연구 질문 하나를 실험 ID 하나로 관리합니다. baseline과 intervention은 같은 태스크 집합·채점 기준을 사용합니다.
모델·도구·프롬프트·예산·실행 순서 중 달라지는 요소와 고정하는 요소를 카드에 명시하세요.
개입 여러 개를 동시에 바꾸면 각 효과를 분리해서 주장하지 마세요.

서로 다른 벤치마크의 절대 점수는 합산하지 않습니다. 각 연구 안에서의 변화와 조건·한계를 종합합니다.
5회 반복은 시즌의 최소 반복 기준이자 초기 점검 출발점입니다. 본 실험의 충분한 표본 크기라는 뜻은 아닙니다.
서로 다른 태스크 수와 태스크당 반복 횟수를 구분하고, 본 실험의 반복·표본 계획과 불확실성 추정 방법을 작성하세요.
seed를 지원하지 않는 API라면 지원하지 않는다고 적고 모델 버전·실행 시각·순서·sampling 설정을 기록합니다.

## Trial: 시도 한 번당 한 행

`trials.jsonl`은 태스크 × 조건 × 반복 한 번당 JSON 객체 한 줄입니다.
[필드 규격](../harness/schemas/trial.schema.json)을 참고하세요.

- `run_id`, `task_id`, `condition` (`baseline` / `intervention`), `repeat_id` (1부터)
- `status`: `success`, `failure`, `error`, `timeout`
- `score`: 연구에서 정의한 수치 또는 미측정 `null`
- `latency_ms`, `input_tokens`, `output_tokens`, `cost_usd`: 측정값 또는 `null`
- `missing_reasons`: 미측정 필드별 이유
- `evidence`: 적용된 개입·응답·채점 근거를 찾을 수 있는 공개 기록

오류·timeout도 행을 남기고 시도 성공률의 분모에 포함합니다. 재시도는 정책과 개별 시도를 추적할 방법을 명시하세요.
키가 빠진 것과 미측정은 다릅니다. 미측정은 `null`과 이유를 사용하고 0으로 채우지 않습니다.
비용은 통화·단가·적용일·실측/추정 여부를 manifest에 기록합니다.

## Run manifest

`manifest.json`에는 실험 ID, run ID, 실행 모드(real/mock), UTC 실행 시각, 코드 commit·dirty 여부,
모델 식별자, 설정 전문, 데이터 버전·체크섬, 반복 계획, 비용 산출 근거를 남깁니다.
실제 연구에서는 의존성 버전과 seed/sampling·실행 순서 정책도 추가하세요.
commit이 dirty라면 그 commit만으로는 코드가 재현되지 않습니다. 제출 시 최종 코드와 당시 실행 코드의 차이를 설명하거나 깨끗한 commit에서 재실행하세요.

## 요약과 reliability

공통 집계기 `harness/summarize.py`는 예시와 같은 **단일 시도·완전한 태스크 × 반복 행렬**을 검증하고 조건별로 집계합니다.
재시도·비대칭 반복 등 다른 설계는 카드에 명시하고 별도 분석기를 제출하세요.

- 성공률: `status=success`인 시도 / 모든 시도
- reliability: 모든 반복에서 성공한 태스크 / 전체 태스크 (`all_repeats_success_rate`)
- 비용 합계: 모든 행의 비용이 측정된 경우에만 계산; 일부라도 미측정이면 `null`

이는 공통 기본 정의입니다. 다른 reliability 정의를 쓰면 이름·분모·수식을 명시하고 기본 값과 혼동하지 않게 하세요.
태스크별 결과·반복 수를 함께 제시해야 하며 모의 실행의 안정성은 실제 모델 안정성의 증거가 아닙니다.
